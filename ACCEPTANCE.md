## Gaps found during final audit and fixed

- /api/docs was404: added self-hosted Swagger and OpenAPI with actual route methods and route-derived Zod payloads. Docs-only CSP permits local assets, not broad API script execution. Read-only UI avoids accidental live mutations.
- Matching reliability previously read never-maintained organization defaults: now aggregates actual no-show/completed outcomes and feedback. Regression verifies score order/components.
- Pickup-before existed in the API but had no frontend filter: local-time control now converts to offset-aware ISO, with UI regression.
  -15minute escalation and expiry-reminder idempotency existed without explicit timed evidence: added integration tests for no early escalation, next NGOs after15minutes, no duplicate notice/reminder.
- README/deployment/security reports contained obsolete pending claims: replaced current status while retaining failure history separately.

## Non-waived production work

Configured external-service success, reliable always-on reminder execution, backups/retention, real topology capacity and independent food-safety/security operations remain needed before real users. No paid upgrade is authorized. Optional OAuth, Sentry and volunteer assignment are explicitly not represented as implemented. Seeded accounts/data are not real organizations or verification proof.

Further UI audit: forecast API supported category selection but dashboard fixed bakery; category selector now exposes all five categories. Socket reconnect now invalidates durable notification/claim/listing queries explicitly, so missed hints do not leave stale dashboard state after reconnect. OpenAPI route-method inventory check is committed as a regression, not only a one-time script.

Final audit also added NGO-personalized nearby food ranking and dashboard cards, not only restaurant-to-NGO recommendations. Same explainable rules score capacity/hours/diet/category/distance, with10km/200candidate bounds and pagination. Endpoint tests cover authenticated success, dietary rejection, invalid query,401and403; UI regression covers ranked food and forecast category.

Returning-client PWA audit found an installed update waiting behind the old offline shell with no prompt UI. Added a visible Update app control with a finish/save-form warning. It never reloads an editing session without a click; activation/controller change then reloads. Real production service-worker lifecycle regression serves two revisions and verifies waiting banner -> explicit click -> new shell. An already-open pre-fix shell cannot render this new control: close old app tabs and reopen once to activate its waiting worker normally. No cache/site-data clearing required. Corrected live NGO layout was inspected after this normal reopen.

Live availability follow-up: provider health probes every5seconds exhausted the shared100/15minute limiter, yielding health429and public502. Health/ready GETs now bypass only that user limiter, with strict input checks unchanged and regression confirming other traffic still hits429. Deployment and a full rate-window runtime observation are required before claiming this incident fixed live. This is separate from expected free-tier sleep.

Performance is a remaining acceptance qualification, not a production-ready pass: the original300ms target is unchanged, and later passing trials do not erase the retained480.35ms durable-storage outlier. No paid upgrade or durability weakening is proposed as an unverified fix.
